# DOOM-E11 stage 4: wiring against chance on the discovered subsystems

**Status: RECONCILED; becomes REGISTERED by the commit that adds this file in this form, before any placement or metric.** Two independent design reviews (a Claude subagent and Gemini `gemini-4-neon-high`) are reconciled in §G; the first draft is replaced because both found that its file shuffle was undefined, its comparison arm unfair, and several predictions unable to fail. Follows [stage 1](../results/e11/E11_STAGE1_RESULTS.md) (stable discovered subsystems), [stage 2](../results/e11/E11_STAGE2_RESULTS.md) (they persist in close copies) and [stage 3](../results/e11/E11_STAGE3_RESULTS.md) (measurement-only placement cannot see them). Engine `704cb35f0`, scanner `b1a9e92`.

## A. Question and what a result can mean
Place each program's functions on `linuxdoom`'s 16 discovered subsystems (S01 to S16), build the program's directed subsystem-to-subsystem call matrix, and compare it with `linuxdoom`'s by cosine, **against chance**: how much of the match comes from where functions were placed, beyond what the call graph's shape and the subsystem sizes alone give? This redoes the scanner's "wiring against chance" (`docs/wiring-against-chance.md`) on the discovered subsystems. The old measure found raw wiring flattered every translation (0.72 to 0.95; Fortran 0.91, 0.80 shuffled) and that against chance Scheme and Go kept DOOM's wiring as well as a C copy, while Java, Kotlin, C# and Fortran showed nothing, a zero that could mean "lost" or "placement failed".
**What this can and cannot say.** Placement (twin, name, file path) is independent of the port's call edges but exists only where code, names or file layout survived, and there the port graph is homologous to the reference's. A positive gap therefore measures *survival of copied code, names and layout together with the wiring of what survived*, not architecture in isolation. To pull these apart, every result is reported **by placement source** (§B). Placement by name and path is **not blind**.

## B. Design
* **Reference:** `linuxdoom` call graph, iterative-consensus Louvain (stage 2 code), resolution **1.0 primary, 0.5 and 2.0 sensitivity**. Reference matrix: directed counts of distinct resolved caller-callee pairs between subsystems. Reported for every reference **before any gap is read**: the diagonal share (fraction of calls inside a subsystem) and the wiring floor (cosine of an all-local program with the reference matrix).
* **Placement rules, derived from `linuxdoom` alone (no hand-tuned per-port rules):** each `linuxdoom` file stem and module prefix (`p_`, `r_`, `am_`, ...) takes the majority subsystem of its functions. Order (as the scanner's `assign`): **(1) structural twin** (E7 Amendment 2 pooled K = 25, strict one-to-one, as in stage 2; same-language ports only); **(2) function name** (normalised, also without a module prefix; **names under six characters and names that map to more than one subsystem in `linuxdoom` are dropped**, since the scanner's first-wins rule let generic names such as `init` or `update` land arbitrarily); **(3) file path** (derived stems then prefixes, longest first); **(4) unplaced** (excluded from the matrix, in every arm; the scanner's `other` class is **not** kept in the matrix).
* **Arms, same programs, scans, engine and exclusion rule:** **D** discovered subsystems with the derived rules (primary); **H1** the scanner's hand-written 16 subsystems with derived rules (same rule richness as D; the fair comparison of *subsystem definitions*); **H3** hand-written subsystems with the scanner's hand-written prefix and keyword rules **without** its per-port overrides; **H2** the full hand taxonomy as shipped (keywords **and** per-port overrides, tuned after seeing the layouts; shown for comparison with the old note, labelled as such).
* **Metrics per program:** **wiring** (cosine of the full matrices) and **cross-wiring** (cosine of the off-diagonal parts), plus the same on `log(1 + count)` (sensitivity); bootstrap interval for cross-wiring from 200 resamples of the program's edges. **Nulls (1,000 draws each; all keep the call graph and the number of placed functions):** **(a) function shuffle** (labels of the placed functions shuffled; the scanner's null); **(b) file shuffle**, defined as **size-stratified profile swap**: placed functions are grouped by source file; files are binned by log2 of their placed-function count; within each bin the files' label lists are permuted among files, each file taking the donor's labels (resampled to its own size); this keeps file cohesion and the file-size and label-purity structure while moving them to other files; **(c) rename**: the 16 subsystem identities permuted. Reported: the real value, each null's mean, SD and 2.5th and 97.5th percentiles, the raw gap, the **standardised gap** (real minus null mean over null SD), the real value's position in the null, and the **minimum detectable gap** (the null's 97.5th percentile minus its mean). **The primary criterion is "above the 97.5th percentile of the file shuffle"**; where the file shuffle is undefined the function shuffle is used and labelled as the weaker null.
* **File null defined only if** the program has at least **30 placed files and no file holds more than 25% of its placed functions** (otherwise reported "file null undefined"; for example `gore` has 12 files with one holding 91%).
* **Results by placement source (the circularity control):** the gap is also computed on **non-twin placements only** (twin-placed functions set to unplaced), and on **twin placements only**, with the same nulls. For programs without twins ('all' equals 'non-twin') this is the primary reading.
* **Placement quality (to read a zero):** per program: functions placed by each source and **coverage** (placed share of code functions); **populated subsystems** (those with at least 3 placed functions); calls per function (resolved-call density against `linuxdoom`'s); Cohen's kappa of name-or-path placement against twin placement on twin-placed functions (same-language only); the **name-versus-path** kappa where both rules apply (a consistency check, not accuracy). **Held-out recovery on `linuxdoom` itself:** five random 20% holdouts, placed by rules and name index derived from the other 80%, accuracy reported; and how well the file-stem and prefix majority reproduces the Louvain labels on `linuxdoom` (communities cut across files, so this caps every score).
* **Scored** only with at least **100 placed functions, 500 directed cross-subsystem calls among them and 8 populated subsystems**; others are listed with their numbers and not scored.
* **Programs and groups, fixed now (as in stage 3):** C close copies, M modified or derived, T translations, R from-scratch rewrites, K toy raycasters, U unrelated, X same-studio and `freedoom`. The expected scored list is not assumed; all programs run and the scored list is an output.
* **Inference:** per program (gap, standardised gap, position in the nulls, interval, minimum detectable gap); group effect sizes as the probability that a random program of one group has a larger standardised gap than one of another (Vargha-Delaney A12) with n and bootstrap intervals, for C against M, M against T, T against U and T against R. No pooled p-values; no multiplicity correction is claimed because the primary predictions are counts, not tests.

## C. Predictions (before any placement)
* **P1 (pipeline sanity, not a test):** each scored close copy (C) has cross-wiring above the 97.5th percentile of every defined null.
* **P2 (primary):** `gore` and `doom-scheme`, if scored, have cross-wiring above the 97.5th percentile of the function shuffle and of the file shuffle where defined, **and above it on the non-twin placements** (they have no twins). If a program is not scored, P2 is untestable for it and is reported so.
* **P3 (primary, controls):** among scored U and R programs at most **one** is above the 97.5th percentile of the file shuffle (function shuffle where the file null is undefined). The minimum detectable gap of each is reported so a wide null cannot make P3 pass by weakness.
* **P4 (primary, the zeros):** for `mochadoom`, `kocoa-doom`, `managed-doom` and `doomf77`: **falsified if any scored one is above the 97.5th percentile of the file shuffle.** For each, the sufficiency gates are reported (coverage at least 0.50, at least 10 populated subsystems, at least 50 functions placeable by both name and path); a zero is called **readable** only if all gates pass and **unreadable** otherwise (placement failed or architecture lost; this method cannot tell).
* **P5 (fair comparison):** over programs scored under both D and H3, the rank agreement (Spearman) of standardised cross-wiring gaps is at least 0.8, and also at least 0.8 within M and T alone; the same against H1 and H2 is reported.
* **P6 (modified ports, the real test):** at least four of the scored M programs are above the 97.5th percentile of the file shuffle under D on **non-twin placements**.
* **P7 (robustness):** rank agreement (Spearman) of standardised gaps across resolutions 0.5, 1.0 and 2.0 is at least 0.8 over programs scored at both, and the scored status of C, T and U programs is unchanged.
Failed predictions are reported as failed. Descriptive: arm comparison, source subsets, placement diagnostics, group effect sizes.

## D. Limits
Names and paths are not blind; ports that renamed and reorganised the most place poorly, and a zero there cannot separate "lost" from "failed placement" (the diagnostics say which). Rules derived from `linuxdoom`'s files cap placement quality (the cap is measured). Both nulls keep the call graph and cannot say whether the calls kept the design. The reference partition is optimised on its own graph, so its matrix has a high diagonal share (reported), unlike the hand-written subsystems. Matrices are counts of distinct resolved calls; unresolved calls (virtual dispatch, interface calls) are not seen, which the calls-per-function diagnostic exposes. 16 is a setting (11 to 24). Third-party source is not committed.

## E. Reporting
Per program and arm: placement counts by source, coverage, populated subsystems, reference diagonal share and floor, wiring and cross-wiring (raw and log), nulls, gaps, standardised gaps, intervals, minimum detectable gap, source subsets, placement diagnostics; the held-out recovery table; group effect sizes; predictions scored.

## F. Not done here
No blind wiring (shown in the earlier study to be manufactured by the method); no ancestry claim; no verdict that architecture was preserved or lost for any program whose zero is unreadable.

## G. Reviews and reconciliation
**Both agreed (and adopted):** the file shuffle as drafted was undefined for files whose functions carry mixed labels and broke subsystem sizes, and was degenerate for flat or few-file layouts; it is now the size-stratified profile swap with a floor (30 files, none over 25%), the file-null-undefined rule and a rename null; the hand-written arm was unfair (50 keyword rules and seven per-port overrides against stems and prefixes), so arms H1 and H3 are added and H2 kept only for comparison with the old note; the scanner keeps `other` inside the matrix and let the first name win; both fixed; P1 was a copy-dominated sanity check and is relabelled; P3 and P4 could pass vacuously or by weakness, so a minimum detectable gap, an explicit falsifier and sufficiency gates are added; P6 as drafted (file null no larger than function null) is not guaranteed (Gemini's Jensen argument) and is dropped for a descriptive comparison, and P7 on signs near zero is replaced by rank agreement; the 16 x 16 off-diagonal cosine is sparse at 100 cross calls, so the floor is 500 with a populated-subsystem floor, log-weight sensitivity, standardised gaps and edge-bootstrap intervals.
**Adopted from the Claude review:** results by placement source (twin only, non-twin only) because twin and name placement make the gap partly a measure of copied-code survival; the reference diagonal share and floor reported first; the held-out recovery test on `linuxdoom` and the file-stem majority cap; a real prediction on M programs (P6) instead of the close-copy tautology; group effect sizes with n and intervals.
**Adopted from the Gemini review:** the three-arm comparison with the same exclusion rule; the name-only versus full-pipeline reading through the source subsets; resolved-call density as a diagnostic for dispatch loss; the A12 effect size and fixed group pairs.
**Declined or limited:** a directory-block null for flat layouts (the file-null-undefined rule is used instead, and gore's stricter-null gap is therefore reported as unmeasurable); Holm correction (the primary predictions are counts, not tests).
