# DOOM-E11 stage 4 (DRAFT, not registered): wiring against chance on the discovered subsystems

**Status: DRAFT 2026-11-25. Becomes REGISTERED when two independent design reviews are reconciled in a dated section and this file is committed before any placement or metric.** Follows [stage 1](../results/e11/E11_STAGE1_RESULTS.md) (stable discovered subsystems), [stage 2](../results/e11/E11_STAGE2_RESULTS.md) (they persist in close copies) and [stage 3](../results/e11/E11_STAGE3_RESULTS.md) (measurement-only placement cannot see them). This is the route stage 3 left open: **non-blind placement by structural twin, function name and file path, scored against chance**, a redo of the scanner's "wiring against chance" (`docs/wiring-against-chance.md`) on the discovered subsystems instead of the hand-written 16.

## Question
For each program, place its functions on `linuxdoom`'s 16 discovered subsystems (S01 to S16), build the program's directed subsystem-to-subsystem call matrix, and compare it with `linuxdoom`'s by cosine, **against chance**: how much of the match comes from where functions were placed, over and above what the call graph's shape and the subsystem sizes alone give? The old measure found that raw wiring flattered every translation (0.72 to 0.95; the Fortran port 0.91, 0.80 shuffled) and that against chance the Scheme and Go ports kept DOOM's wiring as well as a C copy, while Java, Kotlin, C# and Fortran showed nothing, a zero that could mean "lost" or "the placement failed". This stage repeats it with the new subsystems and a stricter null, and reports placement quality so a zero can be read.

## Design
* **Reference:** `linuxdoom` call graph, iterative-consensus Louvain (stage 2 code), resolution 1.0 primary, 0.5 and 2.0 sensitivity. The reference call matrix is the directed count of calls between its discovered subsystems.
* **Placement rules, derived from `linuxdoom` alone (no hand-tuned per-port rules):** each `linuxdoom` source file and each module prefix (`p_`, `r_`, `am_`, ...) takes the majority discovered subsystem of its functions; ports are placed by the sfs `assign` order: **(1) structural twin** (E7 Amendment 2 pooled K = 25, one-to-one as in stage 2) **(2) function name** (the sfs normalised-name rule against `linuxdoom`'s function names) **(3) file path** (derived file-stem and module-prefix rules, longest first) **(4) fallback** (unplaced, excluded from the matrix). The twin step applies only where twins exist (same language); names and paths are **not blind** and the result is labelled that way.
* **Comparison arm, same pipeline:** the scanner's **hand-written taxonomy** (`examples/doom/subsystems.json`, with its hand-written per-port overrides) as the reference, with `linuxdoom` placed by its own rules, so the two sets of subsystems are compared on the same programs, scans and engine (`704cb35f0`).
* **Metrics per program:** **wiring** (cosine of the full matrices) and **cross-wiring** (cosine of the off-diagonal parts); the **wiring floor** (a program whose calls all stay local scores this against the reference); **chance** from two nulls, 1,000 draws each, both keeping the call graph: **(a) function shuffle** (labels of the placed functions shuffled, subsystem sizes kept; the scanner's null) and **(b) file shuffle** (subsystem labels permuted across the program's source files, so functions of a file stay together; stricter, because file cohesion alone drives a lot of wiring); **gap** = real minus null mean, with the position of the real value in each null's distribution and the null's 2.5th to 97.5th range.
* **Placement quality (so a zero can be read):** per program, functions placed by each source (twin, name, path, fallback) and coverage (share placed, non-fallback); **agreement between name/path placement and twin placement** (Cohen's kappa, on the twin-placed functions) for the programs where both exist; and for others, **agreement between the name rule and the path rule** on functions where both apply. A program is **scored** with at least **100 placed functions and 100 directed cross-subsystem calls among them**; the rest are listed with their coverage and not scored.
* **Programs and groups, fixed now (as in stage 3):** close copies (C), modified or derived (M), translations (T), from-scratch rewrites (R), toy raycasters (K), unrelated (U), same-studio (X); every group assignment is fixed here.
* **Inference:** per program (gap, null range, percentile of the real value), group-level rank effect sizes; only P1 to P4 are primary; no pooled p across programs.

## Predictions (before any placement)
* **P1 (primary, close copies):** for each scored C program, the cross-wiring gap exceeds both nulls' 97.5th percentile and is at least 0.30.
* **P2 (primary, names carry):** `gore` and `doom-scheme` (the two translations whose gaps were +0.50 and +0.51 under the hand taxonomy) have a cross-wiring gap of at least 0.20 over the **file shuffle** as well as the function shuffle.
* **P3 (primary, controls):** every scored unrelated or from-scratch program (U, R) has a real cross-wiring inside the 95% range of the file shuffle (no detectable gap).
* **P4 (primary, the unreadable zeros):** for `mochadoom`, `kocoa-doom`, `managed-doom` and `doomf77`, the gap is not above the file shuffle's 97.5th percentile, **and** their placement coverage or name/path agreement is below that of `gore` (so the zero is reported as "placement failed or architecture lost; this method cannot tell", not as "lost").
* **P5:** program rankings by cross-wiring gap agree between the discovered and the hand-written subsystems (Spearman at least 0.8 over scored programs).
* **P6:** for every scored program the gap over the file shuffle is no larger than the gap over the function shuffle (the file shuffle is the stricter null), and the C, T and U orderings are the same under both.
* **P7:** the signs and the scored/not-scored status in P1 to P4 are the same at resolutions 0.5 and 2.0.
A failed prediction is reported as failed.

## Limits
Names and paths are not blind, and ports that renamed and reorganised the most (Java, Kotlin, C#) are expected to place poorly; a zero gap there cannot be separated from a failed placement (stated above; the scanner's own note says the same). Placement rules are derived from `linuxdoom`'s own files, so ports with different file layouts fall to the fallback; the hand-written arm's per-port overrides are the contrast. Both nulls keep the call graph and cannot say whether the *calls* kept the design. The matrix is directed counts of resolved calls; unresolved calls are not seen. 16 is a setting (11 to 24); the sensitivity arms cover it. Third-party source is not committed.
